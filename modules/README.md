# modules

`modules/` хранит самостоятельные продуктовые модули. Каждый модуль - это отдельный runtime package с собственной продуктовой ответственностью, своими feature, внутренней навигацией, DI, assets и тестами.

> если новая функциональность выглядит как отдельная пользовательская возможность или продуктовая область, которую shell подключает через публичный entry point, её место обычно здесь.

## Что должно храниться в `modules/`

- самостоятельные product capabilities
- module root и публичный entry point пакета
- внутренняя навигация модуля
- feature-first структура внутри модуля
- module-owned repositories, datasources, use case, bloc и presentation code
- assets и тесты, которые принадлежат именно этому продуктовому модулю

## Что не должно храниться в `modules/`

- shared runtime infrastructure, полезная нескольким модулям
- общие contracts между shell и всеми модулями
- repo tooling, генераторы и служебные scripts
- shell-wide orchestration, которое относится к `apps/*`, а не к конкретному модулю

Если функциональность должна использоваться многими модулями как общая зависимость, её место обычно в `packages/`.
Если код нужен только для разработки и CI, его место обычно в `tools/`.

## Как понять, что новой функциональности нужен отдельный модуль

Положите код в `modules/`, если на большинство вопросов ответ `да`:

1. У функциональности есть отдельная продуктовая ответственность, которую можно назвать как capability.
2. У неё есть свой пользовательский сценарий, экран или набор экранов.
3. Она владеет своей внутренней логикой, состоянием, данными и navigation flow.
4. Shell должен подключать её как зависимость, а не собирать её внутренности у себя.
5. Большая часть кода останется продуктово-специфичной даже при росте проекта.

## Когда новый код не нужно выносить в модуль

Не создавайте новый модуль, если:

- это всего лишь shared helper, theme primitive или абстракция над сервисом
- это маленький кусок shell orchestration без собственной продуктовой области
- это внутренняя feature существующего модуля, а не новая capability
- вы пытаетесь вынести модуль только ради будущего переиспользования без текущей границы

Сначала должна появиться продуктовая граница, потом новый модуль.

## Базовая структура модуля

Типичный модуль внутри `modules/` выглядит так:

```text
modules/
  quiz/
    pubspec.yaml
    lib/
      quiz.dart
      src/
        module/
        navigation/
        di/
        features/
          home/
            presentation/
            domain/
            data/
            di/
    assets/
    test/
```

Публично наружу модуль должен отдавать только свой entry point, например `package:quiz/quiz.dart`.
Внутренние `src/*`, repository, bloc, datasource и router не должны становиться внешним API.

## Типичные примеры для `modules/`

- `quiz` как самостоятельный learning flow
- `circle_of_fifths` как отдельный музыкальный продуктовый модуль
- будущий `band_profile` с собственной навигацией и данными о музыкальной группе
- будущий `habit_tracker` или `practice_timer`, если это отдельная capability с собственным UX

## Антипримеры

Не кладите в `modules/`:

- shared `AppThemeController` или design system
- общий DI framework или module contracts
- Firebase/Amplitude/Sentry adapters, если они shared
- генераторы модулей, asset importers и миграционные CLI

Это приведёт к размыванию продуктовой границы и превратит модули в контейнер для "любого крупного кода".

## Признаки хорошего модуля

Хороший модуль в `modules/` обычно имеет:

- собственный `pubspec.yaml`
- один публичный entry point пакета
- явную интеграцию в shell
- внутреннюю DI-конфигурацию
- feature-first организацию кода
- отсутствие зависимости на `apps/*`

Если модулю нужен доступ к общей возможности другого модуля, выносите маленький `mediator` в `packages/*` или связывайте модули через shell, а не напрямую.

## Быстрый выбор между `modules/` и соседними директориями

- Нужен самостоятельный пользовательский flow или capability: `modules/`
- Нужна общая runtime dependency для нескольких пакетов: `packages/`
- Нужен генератор, script или dev tool: `tools/`
