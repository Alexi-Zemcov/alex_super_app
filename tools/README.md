# tools

`tools/` хранит служебный код репозитория, который помогает разрабатывать, проверять, мигрировать или генерировать продуктовый код, но не является частью runtime приложений и модулей.

> если код запускается разработчиком или CI как команда, а не импортируется приложением во время работы, его место здесь.

## Что должно храниться в `tools/`

- генераторы кода, шаблонов и boilerplate
- импортёры, конвертеры и миграционные утилиты для данных и assets
- repo-level CLI и dev-утилиты на Dart, Shell или другом языке
- скрипты для локальной разработки, релизных проверок и автоматизации
- инструменты, которые подготавливают артефакты для модулей или пакетов, но не входят в продуктовый runtime

## Что не должно храниться в `tools/`

- shared runtime-код, который импортируется из `apps/*` или `modules/*`
- продуктовые feature, экраны, use case, repository, datasource
- публичные контракты между shell и модулями
- UI-kit, theme primitives, DI primitives и другой reusable runtime infrastructure

Такой код должен жить в `packages/*` или `modules/*`, в зависимости от его роли.

## Как понять, что новому коду место в `tools/`

Положите код в `tools/`, если на большинство вопросов ответ `да`:

1. Код запускается как команда, а не подключается как runtime dependency.
2. Без этого кода продукт продолжит работать, но команде станет сложнее собирать, генерировать или обслуживать проект.
3. Основной пользователь этого кода - разработчик, CI или release process, а не конечный пользователь приложения.
4. Код может зависеть от формата исходников, assets, API-схем или структуры репозитория, но не должен задавать архитектуру runtime-слоя.

## Когда создавать отдельный tool package

Обычный скрипт достаточно держать в `tools/scripts/`, если он маленький и не требует собственной модели зависимостей.

Отдельный package внутри `tools/` имеет смысл создавать, если:

- у инструмента есть собственный `pubspec.yaml`
- у него появляется `bin/`, `lib/`, тесты и независимая логика
- инструмент переиспользуется в нескольких workflow
- ему нужны отдельные зависимости, которые не стоит смешивать с runtime пакетами

Пример:

```text
tools/
  scripts/
    bootstrap_workspace.sh
    check_module_exports.sh
  icon_codegen/
    pubspec.yaml
    bin/icon_codegen.dart
    lib/
    test/
```

## Типичные примеры для `tools/`

- генератор каркаса нового модуля
- CLI для импорта словарей, карточек, нот или quiz-контента в формат assets
- скрипт проверки, что модули экспортируют только публичный entry point
- утилита, которая собирает design tokens и генерирует runtime файлы
- вспомогательный CI-check для workspace boundaries или naming conventions

## Антипримеры

Не кладите в `tools/`:

- `AppThemeController` или shared widgets
- `AppModuleDescriptor` и другие runtime contracts
- `QuizRepositoryImpl`, `CircleOfFifthsBloc`, screen widgets
- shell routing или orchestration между модулями

Если код нужен в приложении во время выполнения, это уже не `tools/`.

## Практическое правило для будущих расширений

При появлении новой сущности сначала спросите:

- это помогает разрабатывать продукт или само является частью продукта?
- это запускается вручную или импортируется в runtime?
- это можно удалить из сборки приложения без изменения пользовательского поведения?

Если ответ про "служебную утилиту" стабильно положительный, коду место в `tools/`.

## Смежные директории

- `packages/` - shared runtime packages, которые импортируются приложениями и модулями
- `modules/` - самостоятельные продуктовые модули с собственными feature и внутренней навигацией
- `apps/` - runnable hosts и composition roots
