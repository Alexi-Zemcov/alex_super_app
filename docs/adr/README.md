# Architecture Decision Records

Ключевые архитектурные решения проекта, их причины и рассмотренные альтернативы.

---

## ADR-001: Dart Workspaces вместо Melos

**Решение:** использовать нативные Dart Pub Workspaces (Dart 3.6+) без Melos.

**Причины:**

- Workspaces — нативный механизм, встроенный в Dart SDK. Не требует стороннего CLI, дополнительной конфигурации и синхронизации версий инструмента между разработчиками.
- Единый `pubspec.yaml` в корне репозитория — единственная точка конфигурации воркспейса.
- Быстрый анализ: Dart analyzer обрабатывает все пакеты как единое целое.
- Единое разрешение зависимостей без конфликтов версий между пакетами.

**Что даёт Melos, но не нужно сейчас:**

| Возможность | Melos | Workspaces |
|---|---|---|
| Единое разрешение зависимостей | Да (через Workspaces с v7) | Да |
| Кастомные скрипты по пакетам | Да | Нет |
| Version bumping и changelog | Да | Нет |
| Фильтрация и оркестрация команд | Да | Нет |
| Публикация пакетов на pub.dev | Да | Нет |

Melos останется опцией на будущее: начиная с версии 7.x он работает поверх Dart Workspaces, а не заменяет их. Миграция будет аддитивной.

**Альтернативы:** Melos, ручное управление `dependency_overrides`.

## ADR-002: Super App вместо отдельных репозиториев

**Решение:** объединить все пет-проекты в один монорепозиторий с единой точкой входа — Super App.

**Причины:**

- **Видимость.** Отдельные недописанные приложения теряются на телефоне. Единая точка входа гарантирует, что все модули — в том числе незавершённые — всегда на виду и мотивируют к доработке.
- **Практика масштабируемой архитектуры.** Монорепозиторий с модульной архитектурой — это приближение к реальным enterprise-проектам, где десятки команд работают над одной кодовой базой.
- **Портфолио.** Один структурированный монорепозиторий демонстрирует архитектурное мышление убедительнее, чем набор разрозненных мелких проектов.

**Альтернативы:** отдельные репозитории для каждого проекта, multi-repo с общими пакетами через git submodules.

## ADR-003: Provider-based DI вместо get_it / injectable

**Решение:** DI построен на `provider` через собственные абстракции `ScopeModule`, `FeatureScope` и `RouteScope` (пакет `scoped_di`).

**Причины:**

- `provider` привязывает жизненный цикл зависимостей к дереву виджетов. Scope автоматически создаётся и уничтожается вместе с виджетом — нет ручного `dispose` и утечек.
- Прозрачная иерархия: app scope → module scope → feature/route scope. Каждый уровень видит только то, что опубликовано выше.
- `provider` — де-факто стандарт в Flutter-экосистеме, рекомендован командой Flutter и совместим с `flutter_bloc`.
- `ScopeModule` как единица регистрации зависимостей делает DI декларативным и тестируемым.

**Альтернативы:** `get_it` + `injectable` (service locator, не привязан к дереву виджетов), `riverpod` (отдельная экосистема, несовместима с `flutter_bloc`).

## ADR-004: go_router для навигации

**Решение:** использовать `go_router` с кодогенерацией (`go_router_builder`) как единственный навигационный фреймворк.

**Причины:**

- Официальный пакет от команды Flutter — стабильная поддержка и развитие.
- Декларативное описание маршрутов через типизированные роуты (`go_router_builder`) устраняет строковые ошибки.
- `ShellRoute` и вложенная навигация естественно ложатся на архитектуру Super App, где каждый модуль предоставляет свой `rootRoute`.
- Deep linking из коробки.

**Альтернативы:** `auto_route` (кодогенерация, но сторонний), Navigator 2.0 напрямую (низкоуровневый API).

## ADR-005: BLoC вместо Riverpod / MobX

**Решение:** использовать `flutter_bloc` для управления состоянием внутри модулей.

**Причины:**

- Явное разделение событий и состояний делает бизнес-логику предсказуемой и легко тестируемой.
- `bloc_test` даёт лаконичный и выразительный DSL для модульных тестов.
- BLoC не зависит от дерева виджетов в отличие от `ChangeNotifier` — бизнес-логика остаётся чистой от UI.
- Нативная интеграция с `provider` через `BlocProvider`.
- Широкое adoption в enterprise Flutter-проектах — паттерн знаком большинству Flutter-разработчиков.

**Альтернативы:** `riverpod` (своя экосистема DI, несовместима с provider-based подходом), `mobx` (кодогенерация, реактивный подход), `cubit`-only (подмножество BLoC без событий).

## ADR-006: Standalone app-хосты для каждого модуля

**Решение:** помимо `super_app` создать отдельные приложения-хосты (`quiz_app`, `circle_of_fifths_app`) для каждого модуля.

**Причины:**

- **Изоляция при разработке.** Запуск отдельного модуля без загрузки всего Super App ускоряет цикл разработки и горячую перезагрузку.
- **Подготовка к публикации.** Если модуль дорастёт до самостоятельного приложения, инфраструктура для его отделения уже готова.
- **Независимое тестирование.** Интеграционные тесты модуля запускаются в его собственном хосте, без побочных эффектов от других модулей.

**Альтернативы:** единственный `super_app` с флагами для изоляции модулей, flavors/build configurations.

## ADR-007: Кастомные lint-правила (analyzer plugin)

**Решение:** создать собственный пакет `alex_workspace_lints` с кастомными правилами статического анализа.

**Причины:**

- Один из ключевых принципов качественного кода — создание системы ограничений, в которой сложно сделать ошибку. Кастомные lint-правила автоматически ловят нарушения архитектурных конвенций до code review.
- Стандартные `flutter_lints` покрывают общий стиль, но не специфику проекта: границы зависимостей между слоями, запрет прямого импорта `src/` другого модуля, паттерны DI.
- Автоматизация вместо дисциплины: правило в analyzer надёжнее, чем договорённость в документации.

**Статус:** в активной разработке. Инфраструктура плагина создана, первые правила в процессе написания.

**Альтернативы:** только документация и ручное code review, `custom_lint` (Dart-пакет от Remi Rousselet, другой подход к плагинам).
