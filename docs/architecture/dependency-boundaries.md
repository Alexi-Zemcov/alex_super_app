# Границы зависимостей между пакетами

## Когда открывать

- Нужно проверить, допустим ли новый import между пакетами.
- Нужно решить, куда вынести общий контракт или `mediator` для cross-module доступа.
- Нужно понять, может ли один модуль использовать код другого модуля.

## Допустимое направление зависимостей

- `apps/*` могут зависеть от `modules/*`, `packages/core/*` и `packages/integrations/*`
- `modules/*` могут зависеть от `packages/core/*`
- `modules/*` могут зависеть от `packages/integrations/*`, если integration package оформлено как product-agnostic integration boundary и не содержит продуктовую логику конкретного модуля
- `modules/*` не должны зависеть от `apps/*`
- один модуль не должен зависеть от внутренних директорий другого модуля
- `packages/core/*` и `packages/integrations/*` не должны зависеть от `apps/*` и конкретных `modules/*`

## Правило для cross-module взаимодействия

Если модулю нужен доступ к общей возможности, есть два допустимых варианта:

- вынести маленький `mediator` в `packages/core/mediators/*`
- связать модули через shell или coordinator, а не напрямую

Здесь `mediator` - это маленький публичный API на границе между модулями.
Обычно он выражен через `command`, `query` или `observe` интерфейс и скрывает внутренние `bloc`, `repository`, `datasource` и `src/*` другого модуля.

## Правило для `packages/integrations/*`

`packages/integrations/*` нужны для shared-адаптеров над внешними SDK, сервисами и платформенными bridge.

Допустимый профиль такого пакета:

- зависит от third-party SDK, HTTP API или платформенного integration layer
- может зависеть от `packages/core/*`
- не зависит от `apps/*`, конкретных `modules/*` и их внутренних реализаций
- не содержит screen flow, feature orchestration и бизнес-логику конкретного модуля

Когда интеграцию стоит выносить в `packages/integrations/*`:

- она нужна нескольким приложениям или модулям
- нужно скрыть vendor-specific детали за стабильным публичным API
- инициализация и runtime wiring должны быть общими для нескольких пакетов
- либо сама integration boundary уже достаточно стабильна, чтобы поддерживать её отдельно от конкретного модуля

Когда интеграцию не нужно выносить:

- если она нужна только одному модулю и её API ещё не оформился как отдельная стабильная integration boundary, держите её внутри этого модуля
- если она принадлежит только shell-приложению, держите её в `apps/*`
- если вместе с SDK-обвязкой наружу уезжает продуктовая логика, значит граница выбрана неправильно

## Плохие сигналы

- импортировать `src/` другого модуля
- тянуть `repository_impl`, `bloc`, `datasource` из соседнего модуля
- делать `apps/super_app` местом общей бизнес-логики модулей
- тащить продуктовые зависимости в `packages/*`
- выносить в `packages/integrations/*` адаптер, который используется ровно в одном модуле и при этом не оформляет отдельную стабильную integration boundary

## Практическое правило

Если новый import ломает одно из этих ограничений, значит граница выбрана неправильно:

- либо нужен маленький `mediator` в `packages/core/mediators/*`
- либо нужен product-agnostic integration package в `packages/integrations/*`
- либо orchestration должен остаться в shell
- либо код должен жить внутри того модуля, которому он принадлежит
