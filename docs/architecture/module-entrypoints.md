# Подключение модуля и публичный entry point

## Когда открывать

- Нужно подключить новый модуль к `apps/super_app`.
- Нужно оформить публичный API модуля.
- Нужно понять, как shell должен видеть модуль.

## Базовое правило

Shell должен импортировать модуль через один entry point, например `package:quiz/quiz.dart`.

Модуль экспортирует наружу только маленький контракт подключения, а не внутренние `bloc`, `repository_impl`, `datasource` или `src/*`.

## Текущая схема

В текущем проекте это выглядит так:

- `module_contracts` объявляет `AppModuleDescriptor`
- модуль публикует `const quizModule = AppModuleDescriptor(...)`
- shell собирает список модулей через явные импорты
- shell передаёт список модулей в свой UI верхнего уровня

Это хороший дефолт для super app:

- shell знает, какие модули подключены
- модуль сам владеет своим root widget, DI и internal routing
- связь между shell и модулем остаётся минимальной и явно типизированной

## Что должен делать модуль

Минимальный публичный API модуля:

1. Иметь один entry point в `lib/<module_name>.dart`.
2. Экспортировать descriptor или factory подключения.
3. Внутри descriptor указывать root builder модуля.
4. Внутри root builder поднимать собственный `FeatureScope` и `Navigator`, если модулю нужна внутренняя навигация.

На примере `quiz`:

- shell импортирует только `package:quiz/quiz.dart`
- модуль публикует только `quizModule`
- внутренние маршруты и DI остаются внутри `modules/quiz`

## Чеклист для нового модуля

1. Создать новый package в `modules/<name>`.
2. Добавить его в root workspace.
3. Описать наружный entry point в `lib/<name>.dart`.
4. Экспортировать из него descriptor или factory для подключения в shell.
5. Подключить пакет в `apps/super_app/pubspec.yaml`.
6. Зарегистрировать модуль в shell явным импортом и добавить в список модулей.

## Чего не делать

- Не импортировать `src/` модуля из shell.
- Не экспортировать наружу внутренние классы data/domain/presentation слоя.
- Не переносить внутреннюю навигацию модуля в shell без явной причины.
