# packages

`packages/` хранит переиспользуемые runtime-пакеты workspace. Это код, который импортируется из приложений и модулей и входит в продуктовую архитектуру как стабильная зависимость.

> если код не является самостоятельной продуктовой областью, но образует отдельную runtime-границу с небольшим публичным API, его место может быть здесь. Фактический reuse несколькими пакетами желателен, но не обязателен с первого дня.

## Что должно храниться в `packages/`

- shared contracts между приложениями, shell и модулями
- маленькие cross-module `mediator`-интерфейсы, если одному модулю нужен доступ к возможности другого
- общая runtime infrastructure
- theme, design system, DI primitives и другие reusable building blocks
- интеграционные адаптеры и abstractions, если они не принадлежат одному конкретному модулю
- небольшие публичные API, на которые могут безопасно зависеть `apps/*` и `modules/*`

Сейчас это особенно относится к `packages/core/*`, а со временем может расширяться и на другие тематические группы вроде `packages/integrations/*`.

## Что не должно храниться в `packages/`

- самостоятельные продуктовые возможности с собственным UX, навигацией и сценарием пользователя
- код, который принадлежит только одному модулю и не является общим runtime API или `mediator`-интерфейсом
- repo tooling, генераторы, миграционные CLI и служебные скрипты
- shell-specific orchestration, которое не должно становиться shared business logic

Если код описывает отдельную пользовательскую возможность, это кандидат в `modules/`.
Если код нужен только разработчикам и CI, это кандидат в `tools/`.

## Как понять, что новому коду место в `packages/`

Положите код в `packages/`, если на большинство вопросов ответ `да`:

1. Код нужен во время выполнения приложения, а не только на этапе разработки.
2. У кода есть небольшой публичный API, который можно поддерживать отдельно от конкретного модуля.
3. На него действительно будут зависеть несколько пакетов, либо это осознанный общий архитектурный слой.
4. Код можно сделать продуктово-нейтральным или хотя бы не привязанным к одному экрану, feature или модулю.

## Когда новый код должен остаться внутри модуля, а не переехать в `packages/`

Оставляйте код внутри `modules/<name>`, если:

- логика обслуживает только один продуктовый модуль
- API ещё нестабилен и плотно связан с внутренними деталями feature
- переиспользование пока гипотетическое, а не фактическое
- вы переносите в общий пакет не `mediator`-интерфейс, а готовую бизнес-логику конкретного модуля

Правило полезное для расширения репозитория: не выносить код "на всякий случай". Сначала появляется реальная общая граница, потом общий пакет.

## Рекомендуемые подкатегории

### `packages/core/*`

Базовые shared runtime packages без продуктовой специализации.

Типичные кандидаты:

- `app_theme`
- `module_contracts`
- `scoped_di`
- будущий `design_system`

### `packages/integrations/*`

`packages/integrations/*` - это runtime-пакеты для интеграции с внешними сервисами, SDK и платформенными возможностями.

Сюда имеет смысл выносить не саму продуктовую логику, а переиспользуемый адаптер на границе с внешним миром:

- typed wrapper над внешним SDK
- adapter между third-party API и внутренними абстракциями приложения
- общую инициализацию и конфигурацию integration layer
- общие runtime-клиенты, которые нужны нескольким пакетам

У такого пакета обычно есть две цели:

1. изолировать конкретный vendor SDK от остального кода workspace
2. дать нескольким `apps/*` или `modules/*` единый способ работать с интеграцией

Чаще всего такой пакет действительно становится shared для нескольких пакетов. Но его можно выделить и раньше, если вокруг vendor SDK уже есть отдельная, стабильная и product-agnostic integration boundary, которую команда хочет поддерживать как самостоятельный API workspace.

Хороший кандидат в `packages/integrations/*`:

- зависит от внешнего SDK, HTTP API или платформенного bridge
- нужен более чем одному package, либо заранее оформляет явную общую integration boundary
- не содержит UI, screen flow и бизнес-логику конкретного модуля
- может иметь собственный публичный API, но не должен тащить за собой внутренности приложений или модулей

Не выносите интеграцию в `packages/integrations/*`, если:

- она нужна только одному модулю, а её API ещё не оформился как отдельная стабильная integration boundary
- она целиком принадлежит shell-приложению
- вместе с адаптером вы переносите продуктовые use case, repository policy или feature orchestration

Практическое правило:

- shared vendor adapter: `packages/integrations/*`
- shell-only wiring: `apps/*`
- module-only integration detail: `modules/<module>/lib/src/...`

Типичные кандидаты:

- analytics adapter
- crash reporting adapter
- shared auth/session bridge
- shared API client wrapper
- shared purchases/billing bridge
- shared remote config adapter

## Типичные примеры для `packages/`

- пакет с публичным контрактом подключения модуля к shell
- `mediator` для cross-module доступа к capability другого модуля
- общая тема и управление темой
- shared design tokens, UI primitives и reusable widgets
- provider/bloc scope primitives
- общая абстракция над persistent storage или аналитикой

## Антипримеры

Не кладите в `packages/`:

- `quiz` flow, `circle_of_fifths` screen logic или module routing
- `super_app`-specific navigation orchestration
- codegen CLI, asset importers и release scripts
- `RepositoryImpl`, `Bloc`, `Cubit`, datasource конкретного модуля, если они не являются частью общего API или `mediator`-интерфейса

Особенно важно не тащить в `packages/core/*` продуктовые зависимости конкретных модулей.

## Признаки хорошего package

Хороший пакет в `packages/` обычно имеет:

- собственный `pubspec.yaml`
- понятный публичный entry point в `lib/<package_name>.dart`
- минимальную поверхность API
- отсутствие зависимости на `apps/*` и конкретные `modules/*`
- тесты на публичное поведение

Если вы создаёте новый workspace package, не забудьте добавить его в корневой `workspace` список в [`pubspec.yaml`](../pubspec.yaml).

## Быстрый выбор между `packages/` и соседними директориями

- Нужен reusable runtime building block: `packages/`
- Нужна самостоятельная продуктовая возможность: `modules/`
- Нужен generator, script или dev CLI: `tools/`
